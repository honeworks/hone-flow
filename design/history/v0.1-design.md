# The first design (v0.1, content-addressed; superseded)

This is hone-flow's first design, kept so a reader can see where the current design started and why it
changed. It was fully built as version 0.1.0 and never published; it was then replaced by run folders
([change 0002](../changes/0002-run-folders.md)). The decision record for it is
[change 0001](../changes/0001-initial-design.md). None of the API below exists today.

## Purpose

Run multi-step workflows whose steps are user code, and handle everything around them: ordering, fan-out
over items, content-addressed assets (local or S3), caching by input content, resume after crashes,
partial runs, human gates, per-step system metrics and full records. No server and no scheduler: a
library and a CLI, built for slow, expensive, non-deterministic AI steps on a local GPU.

Its goals, in the words of the time:

- Steps are plain typed functions; the DAG is inferred from parameter names.
- **Cache by content, not by "done" flags:** key = step name + step version + params + input data
  versions.
- **Resume = cache.** Every finished step is committed immediately and crash-safely.
- **Explain every decision** (`plan`): why each step runs or is skipped.
- **Honest non-determinism:** reused generative outputs are labelled as reused.
- **Human edits are input changes** that invalidate exactly the dependent steps.

Not planned for that version: dynamic fan-out, concurrency pools, remote executors, scheduling, a web UI,
in-step checkpoints, durable replay of code inside a step.

## How it looked to a user

```text
import hone_flow as fk

wf = fk.Workflow("song_video", version="1")      # stores defaulted to .hone/flow/

@wf.step(version="1")
def timeline(item: fk.Item, lyrics: fk.File) -> Timeline: ...

@wf.step(version="1", resources="gpu:ollama", deterministic=False)
def shotlist(timeline: Timeline, style: fk.Param[str], ctx: fk.Context) -> dict: ...

@wf.gate()
def review_shotlist(shotlist: dict) -> dict:
    return shotlist

@wf.step(version="1")
def render(review_shotlist: dict, ctx: fk.Context) -> fk.File: ...

r = wf.run(items, params={"style": "silhouette"})
r.status                                          # "awaiting_review"
wf.approve(r.run_id, step="review_shotlist", item="01")
r = wf.run(items, params={"style": "silhouette"}) # "resumes": cached steps reused, item 01 continues
```

The CLI had `plan`, `run` (with `--from`, `--until`, `--items-filter`, `--no-cache`), `status`, `show`,
`approve`, `edit` (in `$EDITOR`), `reject --note`, `export`, `gc`, `runs` and `pin`.

Notice what this shape implies: there is no "resume" call. Running the same command again is how a run
continued, because every finished step was a cache hit. That was the idea's elegance, and, as it turned
out, its problem.

## The rules

**DAG inference.** Parameters were resolved in order: `fk.Context`, `fk.Item` (by annotation),
`fk.Param[...]` (run-level params), another step's output (by name), an item input, a global step's
output. Unresolvable names and cycles raised `WorkflowDefinitionError`. This part survived unchanged.

**Assets and data versions.** Every return value was stored as an asset: Pydantic models and JSON values
as canonical JSON, `fk.File` as bytes, `fk.Dir` as a manifest listing each file's hash, other types through
registered serializers. An asset's *data version* was the sha256 of its bytes. External input files were
hashed on first use, so editing one invalidated what depended on it.

**The cache key** was the sha256 of the step name, the step version, the params the step used, the data
versions of its inputs in parameter order, and the workflow version. A hit reused the recorded outputs; a
miss recorded its reason: `new`, `input_changed:<name> <old>→<new>`, `version_changed <old>→<new>`,
`param_changed:<name>`, `forced`, `expired`, `cache_disabled`.

**Source changes.** Each step's source was hashed. A changed source with an unchanged version gave a
warning (`source_changed_version_unchanged`) and reused the cache; `strict_versions=True` invalidated
instead.

**Non-deterministic steps.** A cache hit on a `deterministic=False` step was labelled `reused` with the run
it came from; `refresh` forced a new sample and kept the old one as an earlier version.

**Selection.** `fk.Select(only, from_, until, items, force, refresh)` and `cache=False`. `force`,
`refresh` and `from_` implied downstream reruns but not upstream ones; `only` required its inputs to exist.

**Plan.** `wf.plan(...)` returned rows `(item, step, action, reason)` with actions `run`, `cached`,
`reused`, `blocked_by_gate`, `skipped_by_selection` and `warn`.

**Execution.** Breadth-first by default (step A for all items, then step B), with steps sharing a `gpu:`
resources tag batched under one GPU lease. A failing item was marked `failed` with its traceback and the
others continued; `fail_fast=True` stopped the run. The context gave run id, trace id, item id, step,
a stable seed, scratch files and folders, a logger, the trace context and GPU leases.

**Crash safety.** An asset was written to a temporary file, flushed, `fsync`ed and renamed into place; only
then did the metadata transaction commit the execution. Executions left `running` by a dead process
became `interrupted` on the next run.

**Gates.** A gate ran (usually the identity) and stopped its items at `awaiting_review`. `approve` labelled
the output `approved`; `edit` stored a new asset version as the gate's output, so downstream reran;
`reject(note=...)` stored the note as a hidden input of the gated step, available as `review_note`, and
invalidated that step.

**System metrics.** A sampler thread recorded CPU, memory, disk I/O and GPU use while a step ran, as span
summary attributes and `metrics.sample` events.

**Storage.** An `AssetStore` port (`put_bytes`, `put_file`, `open`, `exists`, `delete`, `path_hint`) with
`LocalAssetStore(root)` (files at `root/ab/cd/<sha256>`), `FsspecAssetStore(url)` for S3 with a local
cache, and an in-memory store for tests. The metadata lived in SQLite (`.hone/flow/spans.db`, next to the
span tables): tables `runs`, `executions`, `assets`, `labels`, `gates` and `cache`, documented for
external readers. `export(run_id, dir)` wrote a readable tree; `gc` deleted unreferenced assets except
those of pinned runs; hooks fired when assets were committed or deleted, for a future indexing package.

**Records.** Spans `hone.flow.run`, `hone.flow.step` and `hone.flow.gate`, in the caller's trace.

**The problems it had to prevent** came from the project it was built for: "done" flags ignoring changed
inputs, step lists duplicated in three files, hand-written `--from/--until/--force`, a review note nothing
read, and manual stage batching.

## Its guarantees

Twenty acceptance cases, all of which passed: the end-to-end example (stop at the gate, approve, continue,
export); a second run fully cached with no user function called; one changed lyrics file rerunning only
that item's steps; a version bump rerunning that step and its downstream; the source-change warning and
strict mode; `reused` labels and `refresh`; every selection flag; a SIGKILL mid-run resuming cleanly;
failure isolation; reject with a note; edit; GPU batching; system metrics; records and hooks; the stores
and gc; definition errors; `wf.rerun`; the CLI; and a real Ollama step (the ComfyUI case was skipped:
ComfyUI was not available).

## What happened to it

The build was complete: 195 tests, 98% branch coverage, clean packaging. Reviewing it against real use
showed that a person could not open one folder and see what a run did, that the cache blurred "finish this
run" with "make a new run from old results", and that the SQLite file did not travel with data on S3.
[Change 0002](../changes/0002-run-folders.md) replaced it with self-contained run folders, explicit
resume and fork, and notifications. What survived is listed there under "Kept from the first design".
